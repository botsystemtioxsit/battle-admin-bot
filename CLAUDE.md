# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Telegram bot + Mini App admin panel for "Тролль-Баттл" (repo `index.html`, the game itself). It talks to the **same Firebase Realtime Database** (`zolotaya-kletka`) as the game — there is no separate backend or database for the bot. The panel (`src/admin.html`, ~2200 lines: one `<style>`, HTML, one big inline `<script>`) is itself framework-free, build-free static HTML, same as the game.

### `public/admin.html` is a generated build artifact — never edit it directly
The readable, hand-edited source lives at **`src/admin.html`** — same file, same content, same conventions the rest of this document describes, just moved to that path. **All edits go there.** `public/admin.html` (the file both hosting channels below actually serve) is produced automatically from it: pushing a change to `src/admin.html` on `main` triggers `.github/workflows/build-obfuscated.yml`, which runs `.github/scripts/build-obfuscated.js` (minifies+mangles the inline `<script>` block via `terser`, leaves the CDN `<script src="...">` tags — Firebase, Telegram, JSZip — untouched, validates the result) and commits the regenerated `public/admin.html` (plus `build-id.json` next to it — see the auto-update section below; don't delete or hand-edit it) back to `main`. This repo is deployed through **two independent live channels that both watch `public/`** — Vercel (auto-deploy) and classic GitHub Pages (deploy-from-branch) — and both pick up the rebuilt file automatically once it lands, normally within about a minute. Editing `public/admin.html` directly is pointless: the next push to `src/admin.html` silently overwrites it. This exists for basic protection against casual whole-page copying — it raises the bar for reading the code, but does not prevent someone from simply downloading the served page as-is; the `LICENSE` file at the repo root is the actual legal basis for objecting to unauthorized copies.

Three independent ways to run the *bot* half exist in this repo — pick one, don't run both against the same `BOT_TOKEN`:
- `bot/index.js` — long polling, needs a permanently-running process (systemd unit in `deploy/battle-admin-bot.service`, or Railway via `railway.json`).
- `api/telegram-webhook.js` + `api/_lib/telegram.js` — serverless webhook (Vercel), no persistent process.
- `telegram-serverless/handlers/message.js` — Telegram's own Serverless (BotFather → Serverless → Handlers), no Vercel/Railway at all; see `telegram-serverless/README.md`. Same `/start`/`/admin`/`/help` logic; Mini App URL is hardcoded there (public, not a secret).

Either way, the bot itself decides nothing about access — it only sends a button that opens `public/admin.html` as a Telegram Web App. All access control happens inside `admin.html` itself.

## Commands

No build/lint/test scripts beyond `npm start` (runs `bot/index.js`) — that's for the bot process only, and its `package.json`/`package-lock.json` at repo root are untouched by the admin-panel build (the build workflow installs `terser` standalone in its own step, `--no-save`, so it never modifies or interacts with the bot's dependency tree). `public/admin.html` itself has no dependencies to install, it loads Firebase/Telegram/JSZip SDKs from CDN `<script src>` tags.

Validating a change to **`src/admin.html`** (the file you actually edit — not `public/admin.html`, which is generated; the build workflow separately re-runs an equivalent check against its own output before committing):
```bash
node -e "
const fs = require('fs');
const html = fs.readFileSync('src/admin.html', 'utf8');
const scripts = [...html.matchAll(/<script(?![^>]*src)[^>]*>([\s\S]*?)<\/script>/g)].map(m=>m[1]);
scripts.forEach((s,i) => { try { new Function(s); } catch(e) { console.log('Script', i, 'error:', e.message); } });
const noComments = html.replace(/<!--[\s\S]*?-->/g, '');
console.log('div open/close:', (noComments.match(/<div/g)||[]).length, (noComments.match(/<\/div>/g)||[]).length);
"
```
For visual changes, use Playwright with a stubbed `window.firebase`/`window.Telegram` (see the sibling `index.html` repo's CLAUDE.md — same technique applies here) and screenshot at both a desktop viewport and a narrow mobile one, since `admin.html` has its own `@media (min-width: 900px)` desktop layout. Point Playwright at `src/admin.html` — testing the generated `public/admin.html` is pointless, it's mangled and gets overwritten anyway.

## Architecture

### Access control (`src/admin.html`)
On load it takes `Telegram.WebApp.initDataUnsafe.user.id`, reads `users/<id>/role` from the shared RTDB, and shows "Доступ запрещён" unless the role is `moderator`, `admin`, or `superadmin`. Beyond that gate, **fine-grained permissions** (not fixed role tiers) decide what a given `admin` can actually do — `canManageEvent()`/`canManageClans()`/`canManageBeta()` check per-admin toggles (`users/<uid>/permissions/*`), while `canManageRoles()` is hardcoded to `role === 'superadmin'` (granting/revoking roles, and the raw database browser, are never delegable). `applyRoleUI()` hides tabs a user can't use entirely, rather than showing them disabled; the tab-content functions also self-check the same permission (e.g. `if (!canManageClans()) return;`) in case a click reaches them anyway.

### Tabs (`.tabs` / `.subview[data-panel=...]`, wired in one shared click dispatcher)
Панель / Аккаунт / Ивент / Журнал / Ошибки / Кланы / Заявки / **База** / Система (`data-tab` values: panel/account/event/logs/errors/clans/beta/database/danger) / **Эфир** (`live`) / **Терминал** (`terminal`) — see the two terminals below. The dispatcher also does cross-cutting cleanup on every tab switch (e.g. detaching the "База" tab's live Firebase listeners when navigating away — see below) — a new tab that needs teardown-on-leave should hook in there, not add its own listener.

- **"Ошибки"** reads `admin-logs/error-reports.json` from the **`index.html` repo** (not this one) — see that repo's CLAUDE.md for why (this sandbox has no direct Firebase network access; a GitHub Actions workflow bridges it).
- **"База"** (superadmin-only) is a generic, schema-agnostic Firebase RTDB tree browser: the root key list comes from one cheap REST call (`?shallow=true`, avoids pulling the whole DB just to show folder names); expanding a top-level branch attaches a real `db.ref(topKey).on('value', ...)` listener (children below that are rendered from the already-fetched snapshot, no extra reads) and diffs old vs. new snapshots (`dbDeepEqual`/`dbCollectChanges`) to briefly flash (`.flash` / `dbFlash` keyframes) exactly the rows that changed, bubbled up to their visible ancestors. Collapsing a branch calls `.off('value', ...)` — don't leave these attached, that's the whole point of the lazy design.
- **"Система"** (README/some comments still call it "Правила платформы", an older name — code and UI say "Система") is visible to anyone with panel access but self-checks `superadmin` live on every open (`openDangerZone`), not once at login — a demoted admin loses access immediately even if the tab was already open. Gated further by a one-time secret (`config/resetSecret`) that's erased from the database after a successful reset.

### Two terminals: "Эфир" (read-only live broadcast) and "Терминал" (commands, Superadmin only)
Both live at the end of the inline script of `src/admin.html`.

**"Эфир"** (`data-tab="live"`, everyone with panel access) is a live stream of what is happening, not a snapshot like "Журнал": `startLiveBroadcast()` attaches Firebase listeners once per session (call sites: end of `proceedToApp` and the access-token login) and every event is pushed into the buffer with `liveEmit(kind, text, tone)` — `actions` (new `logs` entries, config flag flips: maintenance/lockdown/closedBeta/backupsDisabled — only those known flags are read from `config`, it also holds secrets), `requests` (login/device requests, from `startLiveRequestWatchers`), `errors` (new `errorReports`), `players` (new `users` by `createdAt`), `matches` (finished `matches` by `finishedAt`), plus the live "онлайн" counter (`presence`) and the connection state (`.info/connected` → "НЕТ СВЯЗИ" instead of a silently frozen feed; the first `false` before any connection is just "ПОДКЛЮЧЕНИЕ…", "потеряна"/"восстановлена" lines are printed only after a connection existed). `config` is read flag by flag (`config/<flag>`), never as a whole node (it holds secrets); `users/token_<token>` keys contain an access token and are never printed. "Only new" is done with `orderByKey().startAt(lastKey)` for push-keyed nodes, and with `orderByChild(field).startAt(now-30s)` for the two time-based ones — **those need `users.createdAt` / `matches.finishedAt` indexes and are only subscribed after `rtdbIndexExists()` says the index exists** (otherwise one system line, never a whole-table download; `rtdbIndexExists` is tri-state: true / false = HTTP 400 "Index not defined" / null = could not check — network, 429, 5xx — which is not cached and is retried once after a minute — with the *original* "since" time, so a player who arrived while the probe was down is not lost). The "· вы" mark on a log line comes only from `ownLogKeys` (keys this page pushed itself in `logAction`), never from the `actorPlayerId` field, which anyone can write. Buffer 500 lines, filter chips, pause (events queue up), follow-the-tail with a "↓ новое" button, a counter on the tab while it is closed (system lines don't count). Read-only: nothing here writes or executes anything.

**"Терминал"** (`data-tab="terminal"`, **Superadmin only**: hidden in `applyRoleUI`, and `termOpen`/`termSubmit` re-check `canManageRoles()`) is the in-app counterpart of `cli/battle-admin.js`: `find`, `ban`, `restrict`, `unban`, `requests` / `approve` / `deny`, `log`, `online`, `maintenance`, `lockdown`, `whoami`, `help`, `clear`. It is **another way to press the same buttons, not a bypass**: bans go through the Worker (`setUserStatus` → `/set-status`), device approvals through `approveDeviceTrustRequest` (shared with the list buttons → `/trust-device`; it refuses if the request changed after the question was shown), `config/*` commands re-read the live role/permission (`termRequireLiveRole`), destructive ones ask y/N, and every mutating command writes the same Журнал action types as the buttons with "(Терминал)" in the details. **Pasting several lines = a batch** (`termPlanBatch`): lines are first normalized (`termNormalizeLine`: copied `$`/`battle>` prompts, code fences, typographic quotes, NBSP/zero-width/bidi characters — the list shows exactly what will run), then every line is validated up front (known command, allowed, per-command `check()` of the arguments, ≤300 chars), `approve`/`deny` are **refused in batches** (their number is resolved after the single y/N, so a request planted in between would be approved blind), the list is printed with a warning about the changing commands, and ONE y/N confirms the lot. Execution context is per run, not global: `termWithTimeout` hands every command its own `ctx` (`{auto, cancelled}`); inside a confirmed batch `ctx.auto` makes `termAsk` answer yes for that line only, and a command that timed out gets `ctx.cancelled`, so when it finally wakes up it can neither self-confirm inside someone else's batch nor plant a stale question. Every command that writes after an `await` calls `termAssertLive(ctx)` first (unban, maintenance, lockdown, deny, …), so a late command writes nothing; `termAsk` refuses a non-auto question once the tab has been left (`!termActive`). A `PLR-…` id that belongs to several accounts stops the command (`termResolveUser`) and is refused for ban/restrict/unban inside a batch (`TERM_ID_ONLY_IN_BATCH`: it would be resolved only after the single y/N) — use the telegram-id there; `ban`/`restrict` refuse your own id at plan time. Lines run one by one with a 30 s timeout each, the first error stops the batch; blank lines and `#` comments are skipped, max 50 lines. This is the intended way to run a block of commands that someone (e.g. Claude) wrote for the owner — it is deliberately **not** a Linux shell: there is no server, and wiring a page that reads a world-writable database to a real shell (local or on a CI runner) would turn any stored XSS into remote code execution.
Everything either terminal prints goes through `textContent`, and every database-derived value is first collapsed to one short line by `termClean` (newlines would let anyone forge terminal lines such as a fake `[y/N]` prompt, and huge values froze the page). New commands = one entry in the `TERM_COMMANDS` `Map` (so `constructor`/`__proto__` are just unknown commands); ids are validated (`TERM_ID_RE`, `PLR-…`) before they become part of a database path.

### Layout and menu ("Полочки", v5.18) — same mechanism on phone and desktop
The look is the owner-picked design "1 · Полочки": a dark sidebar menu with sections grouped on shelves — **Игроки** (Панель, Заявки) / **Контент** (Ивент) / **Наблюдение** (Журнал, Эфир, Статистика) / **Инструменты** (Терминал, Приложения) / **Доступ** (Аккаунт, Супердоступ) — plus an `<h1>` + one-line subtitle above every section. Rules to keep when touching it:
- The tab elements stay `.tab[data-tab]` inside `#app-tabs`; all code keys off `data-tab`, never off order or text (the group headings `.tab-grp` are deliberately **not** `.tab`, so the tab dispatcher ignores them). `applyRoleUI` hides tabs with `style.display`; at its end `syncTabGroups()` hides a group heading whose tabs are all hidden. A new section = one `.tab` in the right group with `data-title`/`data-sub` (they feed `#page-title`/`#page-sub` via `syncPageHead()`, which runs from a click listener on `#app-tabs` *after* the per-tab dispatcher).
- **Same elements, two placements.** `showScreen()` sets `body.in-app` only for `screen-app` (login/denied screens keep the old centred layout). ≥900px: `.topbar` (brand + version), `.tabs` and `.me` are `position:fixed` into one left column (`--side-w`, backed by `body.in-app::before`), and `#screen-app` is a grid (content column, optional `has-db-peek` column of 280px). <900px: the same `.tabs` is a slide-in drawer under a sticky topbar with a ≡ button (`#menu-btn`, `setMenuOpen()`, `body.menu-open`, backdrop, Esc, closes on tab click); the red number on ≡ (`updateMenuCount`, called from `setTabDot`) sums the "Аккаунт" + "Супердоступ" request counters (not the "Эфир" unread count). The topbar is sticky with `z-index:60` on purpose: `.me` (name + «Выйти») lives inside it and is fixed to the drawer's bottom, and a fixed/sticky parent makes its own stacking context.
- **Colours come from `applyPanelTheme()` at runtime, not from `:root`.** The "Оформление" pickers (accent 1/2 + background) feed `derivePanelPalette()`, which writes every `--*` variable inline on `<html>` at startup — so the `:root` block in the CSS is only the pre-JS fallback and **`PANEL_THEME_DEFAULTS` + `derivePanelPalette` are the real palette** (change both together, and the three `<input type=color>` defaults). Text on a filled accent/red button uses `--on-gold`/`--on-live` (picked by `readableOn()`, dark on the light default colours) — don't write `color:#fff` on `var(--gold)`/`var(--live)` backgrounds.
- This was built separately from the game's `.dock-desktop`/`dockOverlayToDevice` overlay-docking system — don't assume shared JS between the two repos beyond the RTDB schema and `emailLogins`.

### Several accounts in the desktop app (v5.19) — Electron only
For testing, the **desktop app** (the Electron window in `desktop/`, detected by `Electron/` in the user agent — `isDesktopApp()`; the wrapper needs no change and no re-release, it just loads the live page) can keep several accounts and switch between them. In browsers, Telegram and the Android app none of it turns on (`.me.switchable` is never set, `rememberAccount` is a no-op). Rules to keep:
- It is a convenience on top of the normal login, **not a new way in.** The session is still the single `localStorage.battleTelegramId`; the list is `localStorage.battleSavedAccounts` = `[{id, name, role, paired, addedAt}]` — nothing secret (no tokens, no `deviceId`; all of it is in the open DB anyway), ids validated by `ACCOUNT_ID_RE`, names rendered only via `textContent`. An account is added only by `rememberAccount()` from `proceedToApp` (i.e. after a login that really went through: owner-approved login request, or pairing code) — "Добавить аккаунт" just clears `battleTelegramId` and shows the normal `screen-login`.
- **Switching = set `battleTelegramId` + reload** (`switchAccount`), so everything is re-checked as on a normal start: role, lockdown, and for admin/superadmin the signed trusted-device entry. The `deviceId` (`battleDeviceSecret`) is one per computer while trust entries are per account, so a newly added admin/superadmin first goes through the usual "device not confirmed" screen — never bypass it for the list.
- The startup "paired-code session whose trust was revoked → kick to login" check (it also used to delete `battleDeviceSecret`) now runs in the desktop app **only for accounts saved with `paired:true`** (set when a pairing code is approved) and no longer deletes the shared device secret there; in every other client it is unchanged. Without this, switching to any account that has no trust entry would have kicked it and wiped the secret every account shares.
- The same list is offered on `screen-login`, `screen-denied`, `screen-device-trust`, `screen-emergency` (`renderAccountChooser`, called from `showScreen`) so a dead-end account never traps you. «Выйти» forgets the current account (`forgetAccount`); the × in the menu forgets another one. Token sessions (`battleAccessToken`) are not part of the list.

### "Аккаунт" — cross-device login without Telegram
**No Firebase Auth, no email sent, ever** — this project must stay on Firebase's free plan, and Firebase Auth's own daily email quota was trivial to exhaust just by testing (this whole mechanism replaced an earlier Firebase Email Link implementation for exactly that reason; don't reintroduce it, and don't propose Blaze/billing as a fix for a Firebase quota). Login is a manual approval flow shared with the game (`index.html`, same CLAUDE.md section there has the full design):
- Attaching an email (Telegram session only, form hidden otherwise) writes `emailLogins/<emailToKey(email)> = telegramId` + `users/<telegramId>/attachedEmail` — refuses if that email already maps to a *different* telegramId, otherwise doesn't verify ownership at all (deliberate; the real gate is the approval tap, not the email).
- `screen-login` (shown when not opened via Telegram) takes an email, looks it up in `emailLogins`, and pushes a request to `users/<foundTelegramId>/loginRequests/<pushId>`, then listens on that exact node (5-minute timeout).
- Approving can happen from **either app**: the game's Community → Запросы tab, or right here in this panel's Account tab (`loadAccountLoginRequests`) — both just flip the same request's `status` to `approved`/`denied`. Once approved, the requesting browser saves `telegramId` to `localStorage.battleTelegramId` and calls `loadAccountAndShowApp` directly.

### Security model (read before "fixing" permission checks)
`database.rules.json` (lives in the `index.html` repo, deploys to the same project) is `.read: true, .write: true` at root, with only two `.validate` rules (a role-enum check, and `battles/$code` requiring `hostId`). There is **no real authorization boundary at the database level** — every permission check described above (role gates, `canManageX()`, the superadmin-only tabs) is a UI convenience, not a security control; anyone with the database URL and browser devtools can bypass all of it directly. This is a deliberate, accepted tradeoff for this project's scale, not an oversight — don't "fix" it by quietly tightening rules without being asked, since `role` itself was intentionally loosened (see README § "Важная оговорка по безопасности") to let the panel grant roles at all.

**Since the role-gateway Cloudflare Worker (`cloudflare-worker/role-gateway/`, see its README) the paragraph above is only partly true** — read this before touching roles, device trust or backups:
- The database is still `.read: true, .write: true` at root, so **nothing stored in it can be both readable and a proof of identity**. Anything the Worker trusts must either be signed by the Worker or come from a Telegram `initData` signature.
- **Trusted devices** (`users/<uid>/trustedDevices/<deviceKey>`): `deviceKey = sha256(deviceId)`; the raw `deviceId` lives only in `localStorage.battleDeviceSecret` and is sent to the Worker over HTTPS, never written to the DB (not in `devicePairings`, `deviceTrustRequests`, logs). An entry counts only with `sig` (HMAC derived from `BOT_TOKEN`), and only `POST /trust-device` creates one. Don't "simplify" this back to existence checks, and never put a raw `deviceId`, token or key into a DB write or a `logAction` string. Pre-v5.8 entries/ids were public, so the storage key was rotated on purpose — never reuse `battleDeviceId`.
- Escape every DB-derived value you put into `innerHTML` (`escapeHtml`), keys included — the DB is writable by anyone, so stored XSS in this panel reaches the superadmin's session.
- **Worker authority comes only from what a caller cannot write:** Telegram `initData`, signed trusted-device entries, and `OWNER_IDS` in `wrangler.toml` (the Worker's superadmins; the DB `role` is erasable/forgeable data and is not used for superadmin actions when `OWNER_IDS` is set). `moderator` is a legacy role that any player can write to themselves, so it is NOT staff for the Worker; backups/`/restore-code`/`/restore-database`/`/grant-role` are superadmin-only (there is no delegable `permissions.backups`).
- **The Worker writes with a service-account OAuth token** (`FIREBASE_SERVICE_ACCOUNT`, `src/firebase-admin.mjs`), which bypasses `database.rules.json`: no secret ever enters the world-readable data (the old `ROLE_GRANT_KEY` scheme leaked it to listeners), and any database path built from caller text must go through `SAFE_ID_RE` first. There is deliberately no fallback to the old scheme — without the secret the Worker answers 500. Deployment is the **Deploy role-gateway Worker** workflow in the `index.html` repo (GitHub secrets are per repository and `FIREBASE_SERVICE_ACCOUNT` lives there); the rules workflow there refuses to run until `/health` shows `firebaseAdminConfigured`. Order: Worker → panel → rules. Don't reintroduce a secret that has to appear inside written data.
- **The bot's updates (login-approval buttons, commands) go to the Worker, not to Vercel / polling / Telegram Serverless.** A tap on an inline button is always delivered to the bot that sent the message, and the Worker sends login-request messages with `BOT_TOKEN` (the "терминал" bot), so the Worker is the bot's only webhook receiver (`POST /telegram-webhook`, registered by the Worker itself on the first login notification via `setWebhook`, secret = `HMAC(BOT_TOKEN, 'telegram-webhook-v1')`, `GET /health` → `telegramWebhook.ours`). `/start`, `/admin`, `/help`, `/requests` are answered by `handleBotMessage` there; `api/telegram-webhook.js`, `bot/index.js` and `telegram-serverless/` no longer receive anything for that bot (the Serverless handlers still serve the *game* bot, but only for buttons that bot sent itself). Login requests carry `app: 'game' | 'admin'` and a `device` label (both writable by anyone — they only shape the message text; never give them any authority), and a button tap is trusted only through `callback_query.from.id`. Details: `cloudflare-worker/role-gateway/README.md`.
- **Known open problem (needs a game-side change):** `/finish-match` still takes the referee/players from a `battles/<id>` record and `playerId` fields any player can write, so points/stars can be forged; the Worker should create and HMAC-sign matches. Only blatant forgery (referee is a participant, self-battle) is rejected.

### Speed — what keeps the panel as snappy as the game
The database is world-readable and holds avatars as base64 inside `users/<id>`, so **reading the whole `users` tree is the one expensive thing** (slow, and it burns Spark's download quota). Rules of thumb that the panel now follows — keep them when adding features:
- Never `db.ref('users').once/on('value')` just to count or filter. The player count comes from `users.json?shallow=true` (keys only); stale-guest cleanup reads only `orderByKey().startAt('guest_')`; the "Администрация" list queries `orderByChild('role').startAt('admin').endAt('superadmin')` (needs `users/.indexOn: role` in `database.rules.json`; `usersRoleIndexExists()` probes with a REST query and falls back to the old whole-tree listener if the index isn't deployed yet — without an index the SDK would download the whole node once per query).
- Every `orderByChild` needs a matching `.indexOn` in `database.rules.json` (index.html repo): `users: playerId, role, pendingNameStatus, createdAt`, `logs: targetKey`, `queue: league`, `matches: finishedAt`, `deviceTrustRequests: status`. Without it the client silently downloads the whole node, and the Worker's REST queries (`getUserByPlayerId`) are rejected with "Index not defined".
- Independent startup reads go out together (`loadAccountAndShowApp`: profile + lockdown + trusted-device record), not in a chain. The backups list (a Worker call + 3 GitHub requests) loads when the Backups section is opened, not at startup. JSZip is loaded on demand (`loadJSZip()`), not by a blocking tag.
- Things a person is waiting on are **live listeners**, not one-shot reads: `startLiveRequestWatchers()` keeps `users/<me>/loginRequests` and (superadmin) `deviceTrustRequests` pending-query live for the whole session and puts a red counter on the "Аккаунт"/"Супердоступ" tabs. New "someone needs an answer" nodes should hook in there.
- The red counters count only **fresh** pending requests (`REQUEST_FRESH_MS`, 10 min: the requesting page deletes its own request after 5 min, but a closed page leaves it `pending` forever, which would keep the counter lit). Fresh = younger than 10 min by `requestedAt` (either direction), **or** it appeared while the panel was open (`requestFirstSeenLive` — `requestedAt` comes from the requester's own clock, which may be minutes off). The lists always show every `pending` request (an old one can still be denied); only the counter/haptic apply the cutoff, and a 30 s timer re-evaluates it. Lists keep the "На 7 дней" selects across re-renders.
- The "Статистика" tab reads six whole trees, so it is cached for 90 s (`STATS_CACHE_MS`); the nickname-review queue uses `orderByChild('pendingNameStatus')`; the Аккаунт tab reads only `attachedEmail`.
- The Worker reads single fields (`getRole`, `getUserField`, `userExists` = `?shallow=true`), never a whole `users/<id>`; `finishMatch` fetches the independent profiles/likes in parallel.

### Auto-update of an open panel (the last `<script>` block of `src/admin.html`)
Same mechanism as in the game (see its CLAUDE.md for the full description: stamped `BUILD_ID`/`BUILD_TIME`, preflight of `?v=<id>&r=<n>`, retry back-off, loop guard in the URL): a **separate last inline block** compares its own stamp (the placeholders `'__BUILD_ID__'`/`'__BUILD_TIME__'` must stay in `src/admin.html` exactly once; `build-obfuscated.js` substitutes them before terser and writes **`public/build-id.json`**, committed with `public/admin.html` — don't delete or hand-edit it) with `build-id.json` next to the page and reloads when it is newer. Busy (= wait, then a pill with "Обновить сейчас" after 8 s): `screen-login` / `screen-device-trust` active, any `fetch` in flight (the block wraps `window.fetch`; this covers role grants and the backup calls), the person edited something in the last 2 minutes (trusted `input`/`change`, so a half-filled event form or terminal input is safe) or a focused field has text, or `window.__updateBusy()` — defined next to the Терминал state: a command is running, a y/N question is pending, or a long operation wrapped in `asLongOp(...)` runs (the restore buttons and "Сделать бэкап сейчас": they have pauses without `fetch` while unzipping/parsing). A new long operation → wrap its handler in `asLongOp`.

### "Бэкапы": selecting and deleting several snapshots
Every list (`list-code-index`, `list-code-admin`, `list-db`) is drawn by `renderBackupList`: a checkbox per row, "Выбрать все", **"Старше 10 дней"** (selects what the nightly pruning would delete: older than `BACKUP_RETENTION_DAYS` by the date in the name, never the `BACKUP_KEEP_NEWEST` = 3 newest) and **"Удалить выбранные (N)"** — one `confirm()` with the count and the first names (a stronger warning if the selection is the whole list), then `POST /delete-backups` (≤100 paths per request, the client chunks; the Worker removes them in **one git commit**, see its README). The two constants must stay equal to `RETENTION_DAYS`/`KEEP_MIN` in `battle-data-admin-bot/.github/scripts/prune-backups.sh`. After any delete (batch or the per-row button) the restore dropdowns are rebuilt (`refreshRestoreSelects`) so a deleted snapshot cannot be picked for restore. Selections live in `backupSelections` (per folder) and survive re-renders.

### Versioning
`#admin-version` in the topbar (a version string + a `title` tooltip summarizing the latest change) is the only version indicator — bump it on every change to this file, the same discipline `index.html` applies to its own `.version-block`.

## Working agreement with the owner

The owner is non-technical and Russian-speaking (often dictates by voice). Standing rules, set by them:
- **Do what is asked and publish it.** For a requested task, finish it, open the PR, merge it, check the result and report — no separate "may I publish?" step. (Worker deploys, releases and the like are part of publishing.)
- **Your own ideas: ask first.** Anything the owner did not ask for (extra features, clean-ups, deleting things) is proposed as a short yes/no question before doing it. Creativity is welcome.
- **Say what limits you**, plainly (e.g. cannot see the phone or PC, cannot set GitHub/Cloudflare secrets or BotFather settings, the sandbox's safety layer blocks some actions such as installing third-party skills into the agent's own config).
- **Write short and plain.** Lead with what happened or what to do; no jargon; one check at a time; skip long explanations — the owner loses the thread in walls of text.
